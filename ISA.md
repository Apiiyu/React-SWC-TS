## Problem

The starter already has useful React, Vite, Vitest, Storybook, and dependency-boundary
configuration, but several quality promises are advisory or split across incompatible sources.
JSDoc requirements and import ordering are not machine-enforced, auto-import declarations have
two tracked destinations, CI uses an unpinned runtime and omits browser tests, startup invokes
`npx`, and builds/tests emit warnings or fail before any Storybook browser test runs. The NestJS
starter provides good governance patterns, but its backend-specific assumptions cannot be copied
into a browser application.

## Vision

A maintainer can clone the starter, run one documented verification matrix, and trust that a green
result means the source is readable, boundaries are intact, generated imports are synchronized,
browser behavior is exercised, and the production build is free of actionable warnings. A new
feature module starts convention-clean instead of creating a cleanup backlog.

## Out of Scope

- NestJS, TypeORM, PostgreSQL, Redis, server health endpoints, migrations, or backend DI patterns.
- Replacing React SWC, Vite, Vitest, Storybook, Zustand, React Query, or the existing module layout.
- Introducing a second formatting, import, or documentation tool when a small deterministic script
  can enforce the convention already chosen by the repository.
- Reworking product UI, authentication semantics, API contracts, or visual design beyond fixes
  required to remove verification warnings.
- Claiming a live SonarQube quality gate passes when repository credentials are unavailable.

## Principles

- A quality promise is either backed by a repeatable probe or remains explicitly advisory.
- One source of truth is better than synchronized copies of generated configuration.
- React-specific constraints outrank backend conventions copied by analogy.
- Local and CI verification must use the same pinned toolchain and command names.
- Warnings that obscure actionable signals are defects in a starter template.
- Views remain thin; feature logic and validation stay behind hooks, schemas, and boundaries.

## Constraints

- The project remains a Bun-managed, ESM Vite React TypeScript application.
- Existing `src/app` and `src/modules` dependency boundaries remain enforced by dependency-cruiser.
- Existing coverage thresholds and bundle-size budgets cannot be lowered.
- Generated auto-import declarations remain generated by `unplugin-auto-import`.
- Browser tests remain opt-in locally but are installed and executed explicitly in CI.
- SonarQube workflow must skip cleanly until repository variables and secrets are configured.

## Goal

Make React-SWC-DDD-TS a reproducible, readable, and maintainable React base project by adapting the
NestJS starter's evidence, JSDoc, import, runtime, CI, and static-analysis discipline to Vite and
React, while removing current warning/error sources and preserving existing application behavior.

## Decisions

- 2026-08-11: Adapt the NestJS governance patterns, not its backend architecture. React needs
  browser-aware checks, TSX support, and Vite-specific runtime parity.
- 2026-08-11: Use deterministic TypeScript scripts for JSDoc and import conventions instead of
  adding multiple ESLint plugins for rules that depend on comments and file paths.
- 2026-08-11: Keep `unplugin-auto-import`; consolidate its generated declaration output rather than
  removing auto-imports, because the existing starter intentionally uses this workflow.
- 2026-08-11: Pin Node 24 in repository metadata and CI. The local machine currently runs Node 26,
  which explains the observed `module.register()` deprecation warning.
- 2026-08-11: Treat Chromium installation as an explicit browser-test prerequisite, not as part
  of ordinary unit-test installation.
- 2026-08-11: SonarQube is an optional CI integration until repository credentials exist; the
  workflow must skip rather than pretend to analyze.
- 2026-08-11: The configured PAI advisor command was unavailable in this environment (the
  repository's `Inference.ts` accepts a different interface and returned exit code 1), so the
  audit findings and fresh command evidence remain the decision boundary.
